# Install Firmware workflow guidance — 2026-09-13

`WorkflowProgress` presents completed milestones for the current selection: catalogue availability, controller/runtime/bootloader identification, firmware selection, artifact validation, target review, programming/verification milestones, and the operation outcome. `WorkflowNextStep` follows the selected source and installation plan, including preparation, inline confirmation, installation, reconnect, and retry guidance. Selecting a different artifact clears the previous operation result.

For local combined HEX, the validation and compatibility section is hidden until preparation succeeds. Online selections show the section immediately, with a validation/retry action; inline DFU confirmation becomes available only after successful HEX inspection. Both sources expose preparation commands. Online selections show catalogue platform, board ID, vehicle family, version, channel, and source before downloading. Local selections immediately show their path and format.

Local HEX platform entry is a selection from known catalogue platforms, independent of release filters. Choosing a local HEX loads these choices directly through the catalogue service without opening or activating the online selector. A load/retry action and status are available beside the local selection. Arbitrary text cannot enable preparation. This is an intended controller target, not board identity extracted from the HEX file. The operator must obtain the target from the file supplier or choose an appropriate online release; filenames and generic STM32 DFU USB identities are not board proof. Payload hash and address ranges remain unavailable until inspection.

The validation section contains an inline `FLASH <platform>` field for both sources. Confirm DFU target accepts only the exact phrase. Editing the phrase, replacing the artifact, changing its platform, or changing the DFU endpoint invalidates review. The review command no longer opens the confirmation dialog. Existing installation-service safety checks remain in place.

Manual DFU entry is an explicit step for a Betaflight controller still running on a serial port. The page shows BOOT-button instructions and the existing manual discovery command; this route does not send an MSP reboot request. Online or local HEX preparation remains available before entry, and the prepared artifact is retained when DFU is detected. Target compatibility is displayed as pending rather than a red false result until evidence permits evaluation. Exact target confirmation and installation remain gated on DFU readiness. The duplicate online validation button is hidden for combined HEX workflows.

HEX preparation errors now direct the operator to review the error and correct the release/file instead of repeating an unchanged validation attempt. A platform/vehicle-variant directory mismatch remains rejected before download, with the selected platform and source directory included in the error. In particular, manual DFU entry does not repair a mismatched `-heli` catalogue source. Verification for this follow-up: all 116 UI tests and 12 DFU artifact resolver tests passed. Manual-entry regressions cover both online and local firmware retention and confirm that neither software reboot nor programming is invoked by that step. No physical flash was performed.

After a successful DFU or serial installation, the page awaits dismissal of the diagnostics report, releases the installation interlock, clears the completed firmware selection and DFU handoff evidence, and selects the first (Information) tab. Serial identity discovery and DFU discovery are refreshed with a 30-second deadline so the landing page reflects the reconnected controller. Failed and cancelled installs retain the firmware selection and current tab. Completion regression tests cover report-dismissal ordering, a reconnected application on a new COM port, cleared DFU state, and both failure outcomes. The UI suite passed all 114 tests after this follow-up; no hardware flash was performed.
