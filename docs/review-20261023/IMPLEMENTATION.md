# Feature parity implementation

Branch: `migration/implement-missing-tasks`. Implementation and verification: **24 October 2026**.

This implements **44 of the 47 groups** from [FEATURE_COMPARISON.md](FEATURE_COMPARISON.md), across Mandatory Hardware, Optional Hardware, Config and Advanced. The other three are explicit scope decisions: output-only mirroring retained (AD-05), historical support proxy unavailable (AD-11), and legacy serial CLI retired (AD-13). Their conditional acceptance criteria permit these choices. No unrelated backlog was reopened.

**Implemented** below means source, application wiring and automated verification are present. It does not mean the workflow has been qualified on a physical vehicle or every historical firmware release. Protocol tests use simulated peers; network tests use localhost. No attached controller, radio, CAN adapter, GNSS receiver, actuator or gamepad was operated.

## Default choices

- Preserve the current navigation, parameter workspace and review/apply/readback design. Use cancellable async commands; synchronous disposal uses the existing observed `SafeFireAndForget` pattern where necessary.
- Resolve controls against reported firmware parameters and preserve native units, unknown enum/bitmask values and unrelated pending edits. Keep ArduPilot scope and postponed localization unchanged.
- AD-05: keep the existing mirror output-only. Selecting both observed directions does not enable inbound commands. No listener/return relay was added.
- AD-11: leave the historical support proxy unavailable; no verified current service endpoint/protocol was supplied. No historical service is contacted automatically.
- AD-13: retain the decision not to restore the obsolete serial CLI. The separate onboard scripting console is implemented.
- Firmware transfers use explicitly selected local images and hardware confirmation. Completion describes transfer/readback evidence; it does not claim a verified successful boot.
- Battery setup uses explicit reported analog pins and calibration values rather than guessing board/sensor presets. RTK receiver changes stay in RAM by default. No default control button mappings are assigned to a joystick.
- Initial Tune values remain starting estimates and require selection. Coupled P/I assistance defaults to 100% (no change), with a bounded 90–110% reviewed adjustment.
- Reduced diagnostic CSV is the privacy-export default. It is not advertised as anonymous or as a complete replayable log.

## Protocol references and choices

- MAVFTP: [protocol](https://mavlink.io/en/services/ftp.html), [ArduPilot server](https://github.com/ArduPilot/ardupilot/blob/master/libraries/GCS_MAVLink/GCS_FTP.cpp). Commands use the existing serialized retry/response machinery and session cleanup. The UI defaults to a new file; a concurrent external writer is outside the protocol's atomic guarantees.
- [NMEA sentence meanings](https://receiverhelp.trimble.com/alloy-gnss/en-us/nmea0183-messages-overview.html): HDT represents true heading. The legacy HDG implementation's use of yaw and fabricated magnetic corrections is not copied.
- Initial Tune recommendations remain historical starting estimates. Nothing is preselected or written automatically; values are mapped only to parameters actually reported by Copter or QuadPlane.

- ESP8266 uses the firmware's byte-wise union encoding, verified against [MavESP8266 source](https://github.com/BeyondRobotix/mavesp8266/blob/master/src/mavesp8266_component.cpp). New text is limited to 15 UTF-8 bytes to reserve a NUL terminator; unchanged legacy 16-byte strings are preserved. Passwords are not logged by the new adapter; raw MAVLink recordings can still contain parameter payloads and should be treated as sensitive.
- CubeID's encapsulated payload reserves 253 wire bytes but uses 252 firmware bytes per sequence, matching the original updater. Local images require explicit hardware matching; remote-ID component identity alone does not identify a board model. No firmware download is selected automatically.
- Joystick uses [Silk.NET.SDL 2.23.0](https://www.nuget.org/packages/Silk.NET.SDL/2.23.0), including its native desktop assets. Four reviewed axes, a held deadman and low throttle are required. Initial enabling requires a disarmed ArduPilot target; no arming command is issued. Button mappings default empty. Input is sampled at 20 Hz; a 250 ms read timeout stops output. RC release uses ArduPilot override semantics; when a link is unavailable, the vehicle's configured RC timeout is the fallback.
- OSD tuning slots use [the firmware OSD parameter-menu protocol](https://ardupilot.org/copter/docs/common-paramosd.html). Numeric custom ranges must be finite with a positive increment; named enumeration types retain firmware-defined bounds.

- Console references: [official Lua REPL setup](https://github.com/ArduPilot/ardupilot/blob/master/libraries/AP_Scripting/applets/repl.md), [MAVLink port adapter](https://github.com/ArduPilot/ardupilot/blob/master/libraries/AP_Scripting/modules/mavport.lua). Current ArduPilot master denies the native REPL start/stop commands; that mode is only for compatible older firmware. Modern applet opening selects a channel with an empty packet and does not execute a newline. Packet loss has no execution acknowledgement; commands are not replayed.
- Parameter presets use the official `Tools/Frame_params` tree and verify the selected immutable blob before saving a local profile. A filename is not evidence of firmware/hardware compatibility. Offline use is through saved profiles. [Reset documentation](https://ardupilot.org/copter/docs/common-parameter-reset.html) documents FORMAT_VERSION=0 and reboot, including the dynamic CAN address table consequence.
- Reduced log export defaults to a strict numeric diagnostic allowlist. It does not attempt to preserve full flight logs while guessing which unknown/vendor payloads are private. The save path must be a new local file (`CreateNew`); existing input/output paths cannot be overwritten. No guarantee of anonymity is made for retained signal patterns.

- Tracker references: [Maestro serial commands](https://www.pololu.com/docs/0J40/5.e), [ArduPilot logical tracker axes](https://github.com/ArduPilot/ardupilot/blob/master/AntennaTracker/mode_servotest.cpp), [mode/servo-power behavior](https://github.com/ArduPilot/ardupilot/blob/master/AntennaTracker/system.cpp). ServoTest implicitly enables servo power. Tests require Stop initially and verify a new stopped/disarmed heartbeat afterward. Standalone travel clamps instead of automatically flipping over the top. ASCII protocols have no pulse-disable command; this limitation is displayed before movement.
- Follow Me defaults to 10 m above HOME and a 100 m maximum target distance, both explicitly reviewed. It does not select Guided or arm. GPS input requires a checksum-valid current GGA fix, at least four satellites and HDOP ≤4; old receiver timestamps, source changes and implausible jumps stop navigation. Moving Base defaults to local-only updates; rally writes are explicitly selected, preserve other points and use MSL altitude plus reviewed clearance.

- RTK base: [u-blox interface specification](https://content.u-blox.com/sites/default/files/documents/u-blox-F9-HPG-1.32_InterfaceDescription_UBX-22008968.pdf) defines TMODE3, NAV-SVIN, NAV-SAT, CFG-PRT and CFG-MSG. Configuration uses acknowledged legacy commands only after support is probed; receivers without these interfaces fail explicitly. Default survey: minimum 60 s, estimated accuracy limit 2 m. Fixed positions use WGS84 ellipsoid height and 0.1 mm accuracy units, not MSL. No automatic persistent save, reboot, baud change or forwarding occurs. Local named presets require review before use. Optional Galileo/BeiDou RTCM messages default off; existing rates are preserved.

- Coupled PID assistance is optional under Extended Tuning. Default 100% makes no change; the allowed 90–110% adjustment scales existing P/I gains together, preserving existing roll/pitch and P:I ratios before firmware-increment rounding. D, feed-forward, integrator limits and unrelated pending edits remain unchanged. This deliberately avoids the old tool's forced equal roll/pitch gains and fixed I:P ratios. The complete before/after preview must be staged explicitly, then applied through the normal parameter workspace. It does not recommend aircraft-specific gains or start autotune.

- DroneCAN defaults: classic CAN v0, maintenance ID 126, CAN 1 Mbit/s, adapter serial 115200, autopilot bus 1. Port selection is explicit. CAN FD and UAVCAN v1 are unsupported. Unknown types remain visible as raw frames; the inspector retains 1,000 frames and exports snapshots, not an unbounded continuous disk log. MAVLink owns the forwarding route, clears capture filters, renews once per second and requests disable on cleanup; close other CAN tools first.
- DroneCAN parameters use GetSet with int64/float32/bool/UTF-8 types, advertised bounds and pre-write conflict/readback checks. Some devices persist writes immediately; ExecuteOpcode SAVE is explicit where supported. Firmware accepts an explicitly confirmed matching local `.bin` up to 4 MiB and serves only the selected node/path with bounded offsets and a ten-minute limit. Completion reports served bytes/EOF, not verified programming or boot. Interrupted updates may require recovery.
- Dynamic ID allocation defaults off and requires a named, confirmed isolated direct SLCAN network without an autopilot/other allocator. Reservations persist before replies; other allocator traffic disables this allocator. Normal flight-controller allocation tables are untouched. No competing distributed allocator is introduced.
- Passthrough defaults to localhost port 2001, RTCM output from one selected node, with incoming writes disabled. Enabled RTCM input validates CRC before bus broadcast. Optional GPS_GENERIC Targetted tunnelling defaults to firmware-selected UART, unchanged baud and no lock. Locking and client writes require explicit review; no u-blox setup or baud-probing commands are injected. Unlock is requested on stop, with AP_Periph's approximately three-second expiry as fallback; previous UART baud is not available for automatic restoration. Local client software can send configuration commands only when writes are explicitly enabled.
- Protocol sources: [DroneCAN transport](https://dronecan.github.io/Specification/4.1_CAN_bus_transport_layer/), [GetSet DSDL](https://github.com/dronecan/DSDL/blob/master/uavcan/protocol/param/11.GetSet.uavcan), [file Read DSDL](https://github.com/dronecan/DSDL/blob/master/uavcan/protocol/file/48.Read.uavcan), [allocation DSDL](https://github.com/dronecan/DSDL/blob/master/uavcan/protocol/dynamic_node_id/1.Allocation.uavcan), [ArduPilot CAN_FORWARD](https://github.com/ArduPilot/ardupilot/blob/master/libraries/AP_CANManager/AP_MAVLinkCAN.cpp), [AP_Periph UART tunnel](https://github.com/ArduPilot/ardupilot/blob/master/Tools/AP_Periph/serial_tunnel.cpp). Implemented afresh behind the existing Core interfaces; no legacy library was imported.

- Radio firmware: Classic SiK checks HEX checksums, nonoverlap, protected flash ranges, board marker and boot signature. The bootloader-reported board/frequency must match before application erase; all data is read back before programming the final validity signature. Parameter erase is never requested. Supports documented classic SiK boards and banked RFD900U/P/mRo900.
- RFD X-series uses exact CHIPID revision matching and 128-byte XMODEM-CRC with ten identical retries, receiver cancellation handling and final EOF acknowledgement before BOOTNEW. Revision-1 images must have board/certified-firmware markers; opaque revision-2 images require explicit manufacturer/hardware confirmation. No temporary reference firmware, country unlock or guessed baud acceleration is used. This path cannot independently read back flash or prove a successful boot. Both paths operate on one local directly attached radio, use explicit image selection and cancellation, and retain recovery guidance. No radio was physically updated.
- Radio protocol references: [official SiK uploader](https://github.com/ArduPilot/SiK/blob/master/Firmware/tools/uploader.py), [bootloader](https://github.com/ArduPilot/SiK/blob/master/Firmware/bootloader/bootloader.c), [flash layout](https://github.com/ArduPilot/SiK/blob/master/Firmware/include/flash_layout.h), [RFD protocol integration](https://github.com/ArduPilot/MissionPlanner/blob/master/SikRadio/RFD900.cs), [RFD XMODEM](https://github.com/ArduPilot/MissionPlanner/blob/master/Radio/XModem.cs). New async implementations use the existing exclusive serial abstraction; no old assemblies were imported.
